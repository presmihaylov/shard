The whole lifecycle, one command each
The same commands on every runtime. One that can’t pause or fork says so, and never falls back.
  1. shard run
    Keeps running after its command exits, until you stop it.
  2. shard stop · start
    Files stay. Processes start fresh.
  3. shard snapshot create
    Saves a stopped sandbox’s files to start new ones from.
  4. shard pause · resume
    Memory is saved too. Processes pick up where they left off.
  5. shard fork
    Copies a running sandbox, memory included. The source keeps going.

Questions
More in the docs
Is it open source?
Yes. shard is licensed under Apache 2.0, and the CLI, the daemon and both SDKs live in one repository on GitHub.
How is it different from hosted sandboxes?
It runs on your own hardware. You control the infrastructure, the data, the access and the isolation, with no hosted service in between.
Do I need /dev/kvm or bare metal?
No. Without /dev/kvm, shard uses gVisor, which runs on an ordinary cloud VM. Only Firecracker needs it.
Where does it run?
On a Linux server on x86-64, or on an Apple silicon Mac with macOS 14 or later. On Windows, run it inside WSL 2.
Does every runtime support every command?
No. runc and Sysbox cannot pause, resume or fork, and say so instead of falling back. shard capabilities shows what a server supports.
How is it different from Docker?
Docker containers share the host kernel. shard adds user-space kernels and VMs, a pause that keeps memory on disk, forks of a running sandbox, egress control and credential brokering.
