To check which version you are running:

```sh
shard version
```

It prints the version of the CLI on a `client` line, then the version of the daemon or server it reaches on a `daemon` line.

To upgrade the CLI, run the installer again. To upgrade a host that setup prepared, run `shard setup` on it and choose to upgrade. Each release on [GitHub](https://github.com/presmihaylov/shard/releases) includes the binaries and their `SHA256SUMS`.

shard is pre-alpha, so a release can change the API, the CLI and the SDKs without any compatibility guarantees.

## v0.1.3

6 October 2026. [Full notes](https://github.com/presmihaylov/shard/releases/tag/v0.1.3).

**New**

- These docs cover install and setup, a quickstart for a server and one for a client, the concepts, the security model, guides, the TypeScript and Python SDKs, a reference and help. The guides that were in the repository's `docs/` folder moved here.
- The [CLI](/docs/reference/cli/) and [REST API](/docs/reference/api/) reference pages are built from the CLI's help text and the API's routes, so they list every command, flag and endpoint of this release.
- Firecracker and vz: the `kernel` field of a sandbox names the guest kernel that it booted, such as `kernel-6.12.110-3`, or `local-` and a hash prefix for a kernel set with `SHARD_KERNEL`. A fork keeps the kernel of its source. gVisor, runc and Sysbox leave the field out.
- `shard create`, `shard fork` and `shard run --detach` print `created sandbox <name>` on stderr for a sandbox with a name. Stdout still holds only the id.

**Install and setup**

- With a saved remote connection, `shard setup` opens on the menu of that connection: check, replace, remove, run sandboxes on this machine, or exit. `--local`, `--provider` or `--start-at-boot` picks the local choice.
- Setup says that a saved connection stores the API key as plain text before it asks whether to save it, not after the save.
- A local setup with no terminal names every flag that it still needs in one error, before any check, and exits 1.
- On Linux, setup also finds a Firecracker disk image in `/var/lib/shard`. When the data belongs to another provider, setup prints the commands that keep or delete it. The delete steps first remove the sandboxes through a daemon of that provider, so their network and cgroups go too. Then they delete the data. With a disk image, they first unmount and remove it, with the same commands as the uninstall note. When shard is not installed yet, the steps first have you choose that provider, so setup installs shard and starts its daemon, and then uninstall shard after the sandboxes are gone. Repair and upgrade stop with the same advice before they change anything.
- On Linux, when only root can read the sandbox records, setup asks for administrator access before its checks. It skips a record that it cannot read, as the daemon does.
- After a failed step, the retry hint names a command that runs: `shard setup`, or the full path of the binary when `shard` is not on `PATH`. With no terminal, the hint also repeats the flags of the run.
- A menu or the step list that gets shorter no longer leaves old lines on the screen.
- The tool download shows its progress for `runsc`, `firecracker` and `sysbox`. A download that gets no data for 30 seconds fails with `no data for 30s`.
- A local setup ends with `shard <version> is set up.`, and a repair with `shard <version> is repaired.`. When the service starts at boot, both say `, and the daemon is running.` instead of the period.
- Setup prints `sudo` only where you need it: never before a shard command on a Mac, and never when you are logged in as root.

**Uninstall**

- On Linux, the note ends with the command that deletes the saved data: `sudo rm -r /var/lib/shard`, and the lock file of the disk image when there is one. After the `sed` that removes the `/etc/fstab` line, it adds `systemctl daemon-reload`.
- On Linux, when the disk image is gone but its `/etc/fstab` line stays, the note names that line and the commands that clean it up, with `umount` first while the data directory is still mounted.
- On a Mac, the note also prints the command that deletes the saved data.

**CLI**

- When the daemon does not answer on a host where setup installed a service that starts at boot, the error says `is the background service running? shard setup repairs it`.
- Errors name the fix as a command or a flag. Errors and help text say API key instead of token, and write shard in lowercase. A command in a hint starts with `sudo` when you ran the CLI with `sudo` against the local daemon.
- `shard snapshot create` on a sandbox whose image is gone names `shard pull <image>`, the command that exists.

**API and SDKs**

- A sandbox or snapshot name with the shape of a generated id gets `400 invalid_request`, not `500 internal`.
- Error messages use plain words and name the fix. Match on `code`, not on the text. The texts of `failed_reason` and `stopped_reason` change too.
- The next release of the `useshards` SDKs carries the same wording in its errors.

**Fixes**

- vz: when the daemon loses its connection to a guest and cannot read the VM state, the sandbox no longer shows as `stopped`. The daemon tries again, then reports the error.
- vz: a connection to a guest that times out no longer leaves a goroutine or a handle in the daemon.
- vz: when the process that runs a VM ends, the sandbox shows as `stopped`, never `running`. A status first waits for the daemon to record the end, for at most 10 seconds once the daemon finds the process gone. Before, it could show as `running` for a while, and for good when the daemon had lost its connection to that process.
- gVisor, runc and Sysbox: the restart count comes back with the exit record, which the host holds, so a process in the sandbox can no longer change it. A file left in `/.shard` no longer makes `stop` or `start` fail.
- `shard rm` no longer fails when the egress log writes into the sandbox directory during the remove.

**Site**

- The landing page has a new design, and these docs take its palette, fonts and logo.
- The installer's banner shows the new logo.

## v0.1.2

5 October 2026. [Full notes](https://github.com/presmihaylov/shard/releases/tag/v0.1.2).

**New**

- One-line install: `curl -fsSL https://useshards.com/install | sh` downloads the newest release, checks it against that release's `SHA256SUMS`, installs it to `~/.local/bin/shard`, and offers to run `shard setup`. The old binary stays in place until the verified new binary replaces it in one rename.

**Install and setup**

- The PATH hint also prints the `export` line for the current shell, so `shard` works without opening a new shell.
- `shard setup --help` lists the setup exit codes.
- For a user that `sudo` does not allow, the administrator check fails immediately and names the reason. A user whose `sudo` needs a password passes only when setup can ask for it at a terminal.
- On a Mac where no local provider can run, setup defaults to a remote connection and says why `vz` is not available. The provider menu marks `vz` as recommended.
- A local setup ends by listing the next steps. When the daemon does not start at boot, it also prints the command that runs the daemon in the foreground.
- Check or repair finds a deleted provider file. An upgrade checks that the restarted daemon answers before it reports the upgrade as done.
- A download that stalls for 30 seconds fails with `connection timed out`, instead of showing a spinner for about 17 minutes. A slow download that is still making progress completes, and a failed download names its cause in plain words.
- On a manual install, setup shows the install's version and provider, and the commands that move it to setup. It leaves the install's files unchanged.

**Uninstall**

- An uninstall removes the bridge and the nft tables when no sandbox or proxy still uses them, and says how to turn `ip_forward` off. It never changes `ip_forward` itself.
- It names what it leaves behind, with the commands that remove it: the data disk image `/var/lib/shard.xfs` on Linux, and the daemon logs in `/var/log/shard` on a Mac.
- On Linux, the refusal that asks you to remove your sandboxes first prints its commands with `sudo`.

**Remote**

- When the server refuses an API key, the error names where the key came from (`SHARD_API_KEY` or the saved connection) and how to fix it. It never prints the key.
- A failed connection names its cause, such as no answer, a self-signed certificate, or a socket that needs `sudo`.

**CLI**

- When an error says the cause is in the daemon log, it names where that log is on this host.
- When shard refuses a create, the error names the flag you type, such as `--memory`, rather than the API field.
- `shard list` prints on stderr how many stopped sandboxes it leaves out.
- `shard exec` on a stopped sandbox refers to the sandbox by its name instead of its id.

## v0.1.1

5 October 2026. [Full notes](https://github.com/presmihaylov/shard/releases/tag/v0.1.1).

**New**

- `shard setup` prepares this host for local sandboxes, with the provider, its tools, the data directory, and a systemd or launchd service. It can also save a connection to a remote server instead.
- The `useshards` SDKs 0.1.0 are on npm and PyPI. They are versioned and released separately from shard.

**Fixes**

- Firecracker: if a create, start, fork or restore is interrupted after its VM has come up, shard now ends that VM.
- macOS and Firecracker: for an image that another provider already pulled, the missing disk format is built offline, without a registry call. The pull streams `building`, then `pulled`.
- macOS and Firecracker: an image already on the host with missing blobs no longer heals itself from the registry. Remove it and pull it again.
- macOS: `stop` no longer fails after 10 seconds while a reconnect to the guest is still in progress.
- Sysbox: `stop` no longer fails when the guest removes one of its own cgroups during the stop. After a daemon restart, `stop` and a forced remove no longer fail on a sandbox whose first process has its standard input on a file the daemon cannot open.
- runc, Sysbox and gVisor: an unreadable memory count is now an error, where before it read as no out-of-memory kill.
- Egress: each sandbox logs its dropped packets under its own rate limit, so one sandbox can no longer silence the drop records of the others.
- Egress: a request that the proxy cannot judge gets a `502` with fixed text and no longer shows the host's nameserver to the sandbox. The cause goes to the daemon log.
- Images: the cache refuses a cached manifest or config that no longer matches its digest, and `shard image ls` lists such an image as `unreadable`.

## v0.1.0

5 October 2026. [Release](https://github.com/presmihaylov/shard/releases/tag/v0.1.0).

The first release:

- `shard` for Linux on x86-64 and for Apple silicon Macs, and a build for Intel Macs, for client use only.
- `shard-init` for Linux, the systemd units for the daemon and for `shard serve`, and the launchd service for a Mac.
- The `useshards` SDKs 0.1.0 for TypeScript and Python, as files on their own GitHub releases. They were on npm and PyPI by v0.1.1.
