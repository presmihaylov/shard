## What is shard?

A sandbox manager for one host. One binary is both the CLI and the daemon. It creates sandboxes from OCI images and keeps each one running between commands:

```sh
shard create --name demo --memory 512MiB alpine:3.20
shard exec demo sh -c 'echo hello from shard > /tmp/hello.txt'
shard exec demo cat /tmp/hello.txt
```

The last command prints `hello from shard`. The file is still there because the sandbox outlives each command. On Linux, run local commands with `sudo`.

## Who is it for?

Anyone who gives an agent a place to run code. The agent's files stay between its commands. You can save its memory while it is idle, or fork it to try another path. The host keeps the secrets and the network policy, outside the sandbox.

## Does shard run sandboxes across many machines?

No. shard manages one host, and does not schedule a fleet. Each host runs its own daemon. A client picks the host with `--remote` or `SHARD_REMOTE`.

## Which machines can host sandboxes?

Linux on x86-64, and Apple silicon Macs with macOS 14 or later. Any other machine, such as an Intel Mac, can run the CLI and connect to a remote server. Linux on ARM has no build. On Windows, run the installer inside WSL 2. [Supported platforms](/docs/install/#supported-platforms) has the table.

## Which provider should I pick?

Let `shard setup` pick. It recommends Firecracker when `/dev/kvm` opens, gVisor on Linux without it, and `vz` on a Mac.

| Provider | Host | Isolation | Pause, resume, fork | Docker inside |
| --- | --- | --- | --- | --- |
| `gvisor` | Linux | a user-space kernel | yes | no |
| `sysbox` | Linux | a user namespace | no | yes |
| `runc` | Linux | none: the host kernel | no | no |
| `firecracker` | Linux with `/dev/kvm` | a microVM | yes | yes |
| `vz` | Apple silicon, macOS 14 or later | a VM | yes | yes |

Setup never picks `sysbox` or `runc`. **Sysbox is for one tenant per host. Use runc only for code you trust.** On runc, root in the sandbox is root on the host. The [provider matrix](https://github.com/presmihaylov/shard/blob/main/docs/provider.md) has every limit.

## Can I change the provider later?

Not under sandboxes that exist. A host's sandboxes stay on the provider that made them, and the daemon refuses another `--provider` over them.

## Do I need Docker?

No. shard pulls images from a registry and drives the runtime itself. To run Docker inside a sandbox, use `sysbox`, `firecracker` or `vz`.

## Does the image's entrypoint run?

No. `shard create` starts no main command, and `shard run` starts the one you give it. The image's `ENTRYPOINT` and `CMD` never run.

## What happens when the main command exits?

The sandbox keeps running, and `shard exec` still works in it. Only `shard stop` or `shard remove` ends a sandbox. There is no idle timer.

## Can a sandbox run systemd?

No. shard's own supervisor is the first process in every sandbox, on every provider.

## What is the difference between stop, pause, fork and snapshot?

| Verb | What it does | Then |
| --- | --- | --- |
| `stop` | frees the memory and keeps the files | `start` runs the main command from the beginning |
| `pause` | saves the memory and the files | `resume` continues the processes where they were |
| `fork` | copies a running sandbox, memory and files | the copy runs as a new sandbox, and the source goes on |
| `snapshot create` | saves the files of a stopped sandbox | `create --snapshot` starts new sandboxes from them |

## Does a sandbox need a memory bound?

On `firecracker` and `vz`, yes. A create without `--memory` is refused there, and the bound is 128 MiB or more. On the other providers, a sandbox with no `--memory` has no memory bound, so set one anyway. A bound larger than the host's memory is refused.

## Can a sandbox read my API keys?

No. Store the key on the host and grant it to the hosts that need it. The sandbox holds only a placeholder. shard puts the real key into the headers of HTTPS requests to those hosts, on the host side. The [secrets reference](https://github.com/presmihaylov/shard/blob/main/docs/secrets.md) has the rules.

## Can a sandbox reach my private network?

No. Without a policy, a sandbox reaches the internet, and the host drops its traffic to private networks, to cloud metadata, to loopback and to other sandboxes. A policy narrows that to the hosts you allow. Sandboxes get IPv4 only. The [egress reference](https://github.com/presmihaylov/shard/blob/main/docs/egress.md) has every rule.

## Does a sandbox survive a reboot?

Its files do. A reboot ends its processes, and the daemon marks it stopped when it comes back. `shard start <name>` starts it again. A restart of the daemon alone ends no sandbox.

## Why do local commands need sudo on Linux?

The daemon's socket belongs to root. On a Mac the daemon runs as your user, and no command needs `sudo`.

## How do I use shard from another machine?

On the server, mint a token with `shard tokens mint`, and run `shard serve` behind an HTTPS proxy. On the other machine, run `shard setup` and choose `Connect to a remote server`. Or set `SHARD_REMOTE` and `SHARD_API_KEY`. The [TCP front](https://github.com/presmihaylov/shard/blob/main/docs/daemon.md#the-tcp-front) has the details.

## Which languages have an SDK?

TypeScript, on Node.js 20.3 or later, and Python, on 3.11 or later. The Python SDK has a synchronous and an asynchronous client. Install them with `npm install useshards` or `pip install useshards`. Any other language can call the REST API. The [OpenAPI schema](https://github.com/presmihaylov/shard/blob/main/docs/openapi.json) describes it.

## How do I upgrade or uninstall?

Run the installer again to get the newest CLI. On a host that setup prepared, run `shard setup` again: it offers to check or repair, to upgrade and to uninstall. An uninstall refuses while a sandbox is left. It keeps your saved data in `/var/lib/shard` and the tools other programs may share.

## Is shard ready for production?

No. shard is pre-alpha. The API, the CLI and the SDKs can change with no compatibility guarantees.
