## What is shard?

shard runs sandboxes for AI agents on hardware you own, a Linux server or an Apple silicon Mac. A sandbox is an isolated Linux environment, and it keeps running between commands:

<Tabs syncKey="lang">
	<TabItem label="CLI">

```sh
# Create a sandbox.
shard create --name demo --memory 512MiB alpine:3.20

# Write a file in it, then read it back. Prints hello from shard.
shard exec demo sh -c 'echo hello from shard > /tmp/hello.txt'
shard exec demo cat /tmp/hello.txt

# Remove the sandbox.
shard remove --force demo
```

	</TabItem>
	<TabItem label="TypeScript">

```ts
import { Shard } from "useshards";

const shard = new Shard();
try {
  // Create a sandbox.
  const demo = await shard.create({ name: "demo", image: "alpine:3.20", memoryMiB: 512 });

  // Write a file in it, then read it back. Prints hello from shard.
  await demo.exec(["sh", "-c", "echo hello from shard > /tmp/hello.txt"]);
  const result = await demo.exec(["cat", "/tmp/hello.txt"]);
  console.log(result.stdout);

  // Remove the sandbox.
  await demo.remove({ force: true });
} finally {
  shard.close();
}
```

	</TabItem>
	<TabItem label="Python">

```python
from useshards import Shard

with Shard() as shard:
    # Create a sandbox.
    demo = shard.create("alpine:3.20", name="demo", memory_mib=512)

    # Write a file in it, then read it back. Prints hello from shard.
    demo.exec(["sh", "-c", "echo hello from shard > /tmp/hello.txt"])
    print(demo.exec(["cat", "/tmp/hello.txt"]).stdout)

    # Remove the sandbox.
    demo.remove(force=True)
```

	</TabItem>
</Tabs>

The `cat` command prints `hello from shard`. The file is still there because the sandbox outlives each command.

The TypeScript and Python examples reach `shard serve` at `SHARD_REMOTE`, with the API key in `SHARD_API_KEY`. [What is shard?](/docs/) has more.

## Who is it for?

It is for anyone who gives an agent a place to run code. shard keeps the agent's files between its commands, and you can save its memory while it is idle or fork it to try another path. The secrets and the network policy stay on the host, outside the sandbox.

## Does shard run sandboxes across many machines?

No. shard manages a single host and does not schedule work across a fleet. Each host runs its own daemon, and a client picks the host with `--remote` or `SHARD_REMOTE`.

## Which machines can host sandboxes?

Linux on x86-64, and Apple silicon Macs with macOS 14 or later. An Intel Mac can run the CLI and connect to a remote server.

There is no build for Linux on ARM. On Windows, run the installer inside WSL 2. [Supported platforms](/docs/install/#supported-platforms) has the full table.

## Which provider should I pick?

Let `shard setup` pick, or see [What provider should I pick?](/docs/choose-provider/), which compares the five and lists every limit.

## Can I change the provider later?

Not while sandboxes exist. A host's sandboxes stay on the provider that created them, and the daemon refuses a different `--provider` while they are there.

## Do I need Docker?

No. shard pulls images from a registry and drives the runtime itself. To run Docker inside a sandbox, use `sysbox`, `firecracker` or `vz`.

## Does the image's entrypoint run?

No. A new sandbox has no processes, and `shard run` starts the command you give it as a named process. The image's `ENTRYPOINT` and `CMD` never run.

## What happens when a process exits?

The sandbox keeps running, and `shard exec` still works in it. The process's restart policy decides whether shard-init starts it again, and `shard ps` shows its state and exit. Only `shard stop` or `shard remove` ends a sandbox, and there is no idle timer. For restart policies, see [Run a long-running server](/docs/essentials/long-running-server/).

## Can a sandbox run systemd?

Not as its first process. shard's own supervisor is the first process in every sandbox, on every provider.

## What is the difference between stop, pause, fork and snapshot?

| Verb | What it does | Then |
| --- | --- | --- |
| `stop` | frees the memory and keeps the files | `start` boots it again and runs its `always` and `unless-stopped` processes from the beginning |
| `pause` | saves the memory and the files | `resume` continues the processes where they left off |
| `fork` | copies a running sandbox, with its memory and files | the copy runs as a new sandbox, and the source keeps running |
| `snapshot create` | saves the files of a stopped sandbox | `create --snapshot` starts new sandboxes from them |

To learn how a sandbox moves between states, see [Sandboxes and the lifecycle](/docs/concepts/lifecycle/).

## Does a sandbox need a memory bound?

On `firecracker` and `vz`, a sandbox always has one. A create without `--memory` gets 512 MiB, and a bound under 128 MiB is refused.

On the other providers, a sandbox without `--memory` has no memory bound, so set one yourself. shard refuses a bound larger than the host's memory. For every bound, see [Resource bounds by provider](/docs/concepts/providers/#resource-bounds-by-provider).

## Can a sandbox read my API keys?

It depends on how you give it the key. Anything that runs in the sandbox can read a key you put there, as an environment variable or in a file.

Store the key as a shard secret instead, and it stays on the host. The sandbox holds only a placeholder, and shard puts the real key into HTTPS requests to the hosts you named. See [Credential brokering](/docs/essentials/credential-brokering/).

## Can a sandbox reach my private network?

No. Without a policy, a sandbox can reach the internet, but the host drops its traffic to private networks, cloud metadata, loopback and other sandboxes. A policy narrows that down to the hosts you allow.

Sandboxes get IPv4 only. The [egress reference](/docs/security/egress/) has every rule.

## Does a sandbox survive a reboot?

Its files do. A reboot ends its processes, and when the daemon comes back it marks the sandbox as stopped. `shard start <name>` starts it again.

Restarting only the daemon does not end any sandbox.

## How do I use shard from another machine?

On the server, mint a token with `shard tokens mint` and run `shard serve` behind an HTTPS proxy. On the other machine, run `shard setup` and choose `Connect to a remote server`, or set `SHARD_REMOTE` and `SHARD_API_KEY`. [Mint a token and connect remotely](/docs/essentials/remote-access/) has the details.

## Which languages have an SDK?

TypeScript, on Node.js 20.3 or later, and Python 3.11 or later. The Python SDK has both a synchronous and an asynchronous client.

Install them with `npm install useshards` or `pip install useshards`. Any other language can call the [REST API](/docs/reference/api/), which the [OpenAPI schema](https://github.com/presmihaylov/shard/blob/main/docs/openapi.json) describes.

## How do I upgrade or uninstall?

On a machine that only connects to a remote server, run the installer again. On a sandbox host, run `shard setup` again, and it offers to check or repair, upgrade, or uninstall.

An uninstall refuses to run while any sandbox remains. It keeps your saved data in `/var/lib/shard`, as well as the tools that other programs may share. [Upgrade](/docs/install/#upgrade) and [Uninstall](/docs/install/#uninstall) have the steps.
