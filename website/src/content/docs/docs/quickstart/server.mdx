Install shard:

```sh
curl -fsSL https://useshards.com/install | sh
```

The installer then offers to start `shard setup`, a wizard that asks how to set up this machine. Or skip the wizard, and set up a Linux host with gVisor in one command:

```sh
shard setup --local --provider gvisor --start-at-boot=true -y
```

Then create a sandbox, run a command in it, and remove it:

```sh
shard create --name demo --memory 512MiB alpine:3.20
shard exec demo echo hello
shard remove --force demo
```

To open a shell in the sandbox, run `shard shell demo` before you remove it.

On a Mac, use `--provider vz`.

## What you need

| Host | Providers | Background service |
| --- | --- | --- |
| Linux, x86_64 | `firecracker` (needs `/dev/kvm`), `gvisor`, `sysbox`, `runc` | systemd |
| macOS 14 or later, Apple silicon | `vz` | launchd |

Setup runs as you and asks for administrator access when a step needs it. An Intel Mac cannot host sandboxes, but it can connect to a remote server.

## Start at boot

When shard starts at boot, setup installs a service and checks that the daemon answers before it reports success.

| | Linux | macOS |
| --- | --- | --- |
| Service file | `/etc/systemd/system/shard.service` | `/Library/LaunchDaemons/shard.daemon.plist` |
| Check it | `systemctl status shard` | `launchctl print system/shard.daemon` |
| Logs | `journalctl -u shard` | `/var/log/shard/daemon.log` |
| Daemon runs as | root | your user |

Both services restart the daemon one second after a crash, and leave it stopped after a clean exit.

A sandbox outlives the daemon. When the daemon stops or restarts, every sandbox keeps running, and the next daemon takes them back.

`shard daemon status` shows the version, the provider, the process details and the background tasks of the running daemon.

## Run the daemon yourself

Otherwise, setup installs the provider's tools and the data directory, but no service. Start the daemon in a terminal of its own, and run your commands in another one:

```sh
shard daemon --provider gvisor
```

On a Mac, run `shard daemon --provider vz`. Closing the terminal ends the daemon. The sandboxes keep running until a daemon takes them back.

## The data directory

The daemon keeps its state in `/var/lib/shard`: the sandbox records, the images, the secrets and the policies. Setup never asks for another directory.

Firecracker copies a disk for each fork and snapshot. That needs a filesystem that clones a file by sharing its blocks: XFS or Btrfs. On any other filesystem, the daemon makes an XFS image at `/var/lib/shard.xfs` and mounts it over `/var/lib/shard`. Setup asks how much space to reserve for it, and offers half the available space, up to 100 GiB. The daemon reserves the whole size when it first starts. Setup refuses Firecracker there when that filesystem has less than 20 GiB free, or when `/var/lib/shard` already holds files. [Firecracker on KVM](/docs/guides/kvm/#the-data-directory) has the details.

## Script it

Each question of the wizard has an option, so a script sets up a host without one:

```sh
shard setup --local --provider firecracker --start-at-boot=true -y
```

- `--local`: run sandboxes on this machine. `--provider` and `--start-at-boot` imply it.
- `--provider <name>`: `firecracker`, `gvisor`, `sysbox`, `runc` or `vz`.
- `--start-at-boot <true|false>`: install a service that starts the daemon at boot.
- `--http-api <true|false>`: also run the HTTP API as a background service, on the address `--listen` names. Off by default.
- `--storage-size <size>`: Firecracker only, the space to reserve for sandbox disks when the filesystem is not XFS or Btrfs.
- `-y`: apply the changes without asking.
