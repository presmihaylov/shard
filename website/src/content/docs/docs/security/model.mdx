shard assumes the code in a sandbox is hostile, and keeps the host, your credentials and your private networks out of its reach.

## What shard protects

shard treats the code in a sandbox as untrusted. That code might be an agent, a tool that a prompt injection took over, or a package nobody has read. It can read its own environment, dump its memory, and send every byte it finds to anywhere it can reach.

Four boundaries separate that code from what you want to protect:

| Boundary | What it keeps out | Where it is enforced |
| --- | --- | --- |
| The provider | the host kernel and other sandboxes | gVisor, a virtual machine, or a user namespace |
| Secrets | the value of a credential | the proxy on the host |
| Network egress | your private networks, and hosts the policy does not allow | the host, never the sandbox |
| The API | anyone without access to the socket or a valid token | the daemon socket and `shard serve` |

## Isolation depends on the provider

The provider decides how strongly a sandbox is isolated from the host and from other sandboxes. gVisor, Firecracker and vz put a kernel of their own between the sandbox and the host, and many tenants can share one host. Sysbox shares the host's kernel and suits one tenant per host, and runc isolates nothing, so use it only for code you trust.

For what each provider puts between a sandbox and the host, see [Isolation by provider](/docs/security/isolation/).

## Secrets never enter the sandbox

A sandbox gets a placeholder for each secret, never the value. The value stays on the host, and the proxy on the host puts it into the headers of HTTPS requests to the hosts the secret is granted to, and nowhere else.

A network policy is enforced on the host too, outside the sandbox, so code in the sandbox cannot change it.

Give a sandbox an API key that it cannot read, and let it reach only `api.openai.com`:

<Tabs syncKey="lang">
	<TabItem label="CLI">

```sh
# Store the key on the host, for api.openai.com only.
printf '%s' "$OPENAI_API_KEY" |
  shard secret set --destination api.openai.com OPENAI_API_KEY

# Allow api.openai.com and deny everything else.
shard policy create --allow api.openai.com --deny any openai-only

# Create a sandbox with the secret and the policy.
shard create --name agent --memory 512MiB \
  --secret OPENAI_API_KEY --policy openai-only alpine:3.20

# Prints mock-OPENAI_API_KEY, not the key.
shard exec agent sh -c 'echo "$OPENAI_API_KEY"'

# Remove the sandbox.
shard remove --force agent
```

```ts
import { Shard } from "useshards";

const shard = new Shard();
try {
  // Store the key on the host, for api.openai.com only.
  await shard.secrets.set("OPENAI_API_KEY", {
    value: process.env.OPENAI_API_KEY!,
    destinations: ["api.openai.com"],
  });

  // Allow api.openai.com and deny everything else.
  await shard.policies.set("openai-only", [
    { action: "allow", rule: "api.openai.com" },
    { action: "deny", rule: "any" },
  ]);

  // Create a sandbox with the secret and the policy.
  const agent = await shard.create({
    name: "agent",
    image: "alpine:3.20",
    memoryMiB: 512,
    secrets: ["OPENAI_API_KEY"],
    policy: "openai-only",
  });

  // Prints mock-OPENAI_API_KEY, not the key.
  const echo = await agent.exec(["sh", "-c", 'echo "$OPENAI_API_KEY"']);
  console.log(echo.stdout);

  // Remove the sandbox.
  await agent.remove({ force: true });
} finally {
  shard.close();
}
```

## The host decides network egress

A sandbox has no network rules of its own. The rules live on the host, so code in the sandbox cannot change them.

Without a policy, a sandbox reaches the internet but nothing private: no private network, no cloud metadata address and no other sandbox. That floor holds under every policy. A policy narrows the rest to the hosts it allows, and a proxy on the host judges web traffic by host name.

For how the host enforces it, see [Network egress](/docs/security/egress/). To write a policy step by step, see [Lock down network access with a policy](/docs/essentials/network-policy/).

## Forwarded ports

`shard port add` forwards a host port to one port of one sandbox. By default the host listens on `127.0.0.1`, so only programs on the host can connect. With `--public` the host listens on `0.0.0.0`.

<Aside type="caution">
A public port is open to every network the host is on. shard does not check who connects. Anyone who reaches the host on that port talks to the program in the sandbox, so forward a port publicly only to a program that checks its own clients. shard leaves the host's firewall as it is, and a firewall that drops the port keeps the forward closed to other machines.
</Aside>

A forward changes nothing about the sandbox's own traffic. The egress floor and the policy still decide what the sandbox can reach.

To forward a port step by step, see [Expose a port of a sandbox](/docs/essentials/expose-a-port/).

## Who can reach the API

The daemon listens only on a unix socket at `<root>/shard.sock`, which defaults to `/var/lib/shard/shard.sock`. It never serves its API on TCP.

The only TCP ports the daemon opens are the egress proxy and resolver on the sandbox gateway, and the host ports that an operator forwards with `shard port add`. A forwarded port carries bytes to one port of one sandbox, and never reaches the API.

The socket has mode `0600`, so only the user the daemon runs as can use it. On Linux that user is root. If the host has a group named `shard`, the daemon hands the socket to that group with mode `0660` when it starts, and members of the group can then use the socket.

<Aside type="caution">
Anyone who can reach the socket holds every right. A request on the socket carries no token and no scopes. Add a user to the `shard` group only if you trust them with every sandbox and every secret on the host.
</Aside>

## Remote access goes through shard serve

A client on another host reaches the daemon through `shard serve`, a separate process that checks a token on every request and then passes the bytes to the socket. By default it listens on `127.0.0.1:7850` and speaks plain HTTP.

<Aside type="caution">
Put an HTTPS proxy or a tunnel in front of shard serve before any token crosses a network. Over plain HTTP, the token travels in clear text. `shard serve` logs a line when it starts if its listen address is not loopback.
</Aside>

- **A bad token never reaches the daemon.** `shard serve` answers `401` to a token that is forged, expired or revoked, before it opens the socket.
- **Scopes limit the routes.** A request outside the token's scopes gets `403`, and so does a create that names a secret, a policy or a port forward the token has no scope for.
- **A revoke takes effect at once.** The next request with the token gets `401`, and `shard serve` closes its open connections within a second.
- **A token without `--duration` never expires.** Nothing rotates the signing key.

For the scopes, and to mint, list and revoke tokens, see [Authentication](/docs/reference/auth/). To set up `shard serve` and its proxy, see [Mint a token and connect remotely](/docs/essentials/remote-access/).

## What shard never writes down

- shard never logs a secret value, and never writes one into a state file. A sandbox record names its secrets but never holds their values.
- The proxy logs one line for each request, but never logs a header value.
- `shard serve` and the CLI never log a token or the signing key. `shard serve` logs the name of the token for each request it lets through.
- `shard secret list` prints names, destinations and placeholders, but never a value.
