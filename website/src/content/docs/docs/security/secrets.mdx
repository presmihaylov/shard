Code in a sandbox can use an API key without ever holding it. The sandbox holds a placeholder, and the host puts the key in on the way out:

<Tabs syncKey="lang">
	<TabItem label="CLI">

```sh
# Store the key on the server, for api.openai.com only.
printf '%s' "$OPENAI_API_KEY" |
  shard secret set --destination api.openai.com OPENAI_API_KEY

# Create a sandbox that holds the placeholder.
shard create --name agent --memory 512MiB --secret OPENAI_API_KEY alpine:3.20

# Prints mock-OPENAI_API_KEY, not the key.
shard exec agent sh -c 'echo "$OPENAI_API_KEY"'

# Remove the sandbox.
shard remove --force agent
```

	</TabItem>
	<TabItem label="TypeScript">

```ts
import { Shard } from "useshards";

const shard = new Shard();
try {
  // Store the key on the server, for api.openai.com only.
  await shard.secrets.set("OPENAI_API_KEY", {
    value: process.env.OPENAI_API_KEY!,
    destinations: ["api.openai.com"],
  });

  // Create a sandbox that holds the placeholder.
  const agent = await shard.create({
    name: "agent",
    image: "alpine:3.20",
    memoryMiB: 512,
    secrets: ["OPENAI_API_KEY"],
  });

  // Prints mock-OPENAI_API_KEY, not the key.
  const echo = await agent.exec(["sh", "-c", 'echo "$OPENAI_API_KEY"']);
  console.log(echo.stdout);

  // Remove the sandbox.
  await agent.remove({ force: true });
} finally {
  shard.close();
}
```

```python
import os

from useshards import Shard

with Shard() as shard:

    # Remove the sandbox.
    agent.remove(force=True)
```

The TypeScript and Python examples reach `shard serve` at the address in `SHARD_REMOTE`, with the API key in `SHARD_API_KEY`.

When code in the sandbox sends that placeholder in a header of an HTTPS request to `api.openai.com`, the host puts the real key in its place. Code that reads its environment, dumps its memory or posts every byte it finds somewhere else gets only the placeholder.

To store, grant, rotate and remove a secret, see [Credential brokering](/docs/essentials/credential-brokering/).

## Where the value lives

- **On the server, in one file.** `shard secret set` writes the value to `<root>/secrets/<NAME>`, with mode `0600`, in a directory with mode `0700`. That file is the only place shard writes the value.
- **Never in a log or a record.** shard never logs a value, and a sandbox record names its secrets but never holds their values. `shard secret list` prints names, destinations and placeholders only.
- **Never in the sandbox.** The sandbox gets the placeholder as `$NAME`, and so does every process that `shard run` starts in it.

## Where the value goes in

The host puts the value in only when all of these are true:

- the request goes over TLS, on port `443`
- the request goes to a destination of the secret
- the placeholder appears exactly, in a header value

Here is what happens to `OPENAI_API_KEY`, granted to `api.openai.com`, in each request from the sandbox:

| Request from the sandbox | What goes out | Why |
| --- | --- | --- |
| `Authorization: Bearer mock-OPENAI_API_KEY` to `https://api.openai.com` | <Badge text="key goes in" variant="success" /> | a header, over HTTPS, to a destination |
| `X-Api-Key: mock-OPENAI_API_KEY` to `https://api.openai.com` | <Badge text="key goes in" variant="success" /> | any end-to-end header works |
| `https://api:mock-OPENAI_API_KEY@api.openai.com` | <Badge text="key goes in" variant="success" /> | the host decodes HTTP Basic auth, puts the value in and encodes it again |
| `Authorization: Bearer mock-OPENAI_API_KEY` to `https://example.com` | <Badge text="placeholder" variant="danger" /> | `example.com` is not a destination |
| `Authorization: Bearer mock-OPENAI_API_KEY` to `http://api.openai.com` | <Badge text="placeholder" variant="danger" /> | plain HTTP crosses the network in clear text |
| `https://api.openai.com/v1/models?key=mock-OPENAI_API_KEY` | <Badge text="placeholder" variant="danger" /> | an upstream can quote the path or the query back in an error |
| `{"key": "mock-OPENAI_API_KEY"}` in the body to `https://api.openai.com` | <Badge text="placeholder" variant="danger" /> | an upstream can quote the body back too |
| the key encoded in base64, or a request signed with it | <Badge text="placeholder" variant="danger" /> | the host sees no placeholder to replace |
| `Proxy-Authorization: mock-OPENAI_API_KEY` | <Badge text="placeholder" variant="danger" /> | a hop-by-hop header belongs to the connection, not the upstream |
| a database password on port `5432`, or SMTP on `587` | <Badge text="placeholder" variant="danger" /> | only port `443` goes through the host's TLS proxy |

The hop-by-hop headers are `Connection`, `Proxy-Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `Te`, `Trailer`, `Transfer-Encoding`, `Upgrade`, and any header that `Connection` names. On any port, the policy still decides whether the connection itself is allowed.

<Aside type="caution" title="Grant a secret only to hosts that never send it back">
The host puts the value into the request, but it never reads the response. A granted host that echoes a header it received, such as an echo endpoint or a debug page, returns the real value to the sandbox.
</Aside>

## What a grant changes

- **A secret goes to destinations, never to a sandbox alone.** A request to a host that is not a destination carries only the placeholder.
- **A wildcard cannot cover a public suffix.** `*.github.com` is accepted, while `*.com`, `*.co.uk` and `*.github.io` are refused, so a grant never reaches every site under a shared suffix.
- **A grant opens no host.** The sandbox's policy still decides what it can reach, so a sandbox with a policy needs an allow rule for each granted host.
- **A grant puts the sandbox behind the egress proxy.** From then on, a TLS handshake with no server name is refused, and a request whose `Host` differs from the handshake name gets a `400`. See [egress](/docs/security/egress/).
- **A fork keeps its source's grants.** A snapshot holds no grants and no policy, so a create from a snapshot needs its own `--secret` and `--policy`.

## A client that does not trust the proxy

The proxy reads HTTPS traffic, so the sandbox trusts the proxy's certificate authority. A client that does not, such as Java with its own keystore or a client that pins a certificate, fails the handshake, and the value is never sent.

To make Java or Rust trust the proxy, see [Credential brokering](/docs/essentials/credential-brokering/#if-a-client-does-not-trust-the-proxy). For what brokering does not stop, see [known limits](/docs/security/limits/).
