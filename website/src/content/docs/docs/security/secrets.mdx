The sandbox prints a placeholder, not the key:

```text
mock-OPENAI_API_KEY
```

When code in the sandbox sends that placeholder in a header of an HTTPS request to `api.openai.com`, the host puts the real key in its place. Code that reads its environment, dumps its memory or posts every byte it finds somewhere else gets only the placeholder.

## Store a secret

`shard secret set` writes the value on the server, to `<root>/secrets/<NAME>`, at mode `0600` in a directory of mode `0700`. That file is the only place shard writes the value.

The name is the environment variable the sandbox reads. It uses uppercase letters, digits and `_`, does not start with a digit, and is at most 128 characters.

`--destination` names a host the value may go to. It is required on the first `set`, and it repeats for each host. `--dest` is the short form.

`shard secret set` takes the value in one of three ways:

- on stdin, when stdin is a pipe or the value is `-`
- at a prompt with the echo off, when you run it at a terminal and give no value
- as an argument after the name

Use stdin in a script. The value then lands in no shell history and no process list. A value given as an argument is stored, but `set` prints a caution on stderr, because the process list showed the value while the command ran.

`shard secret list` prints the columns `NAME`, `DESTINATIONS`, `PLACEHOLDER` and `UPDATED`, and never a value. `--format json` prints the same fields as JSON.

`shard secret remove <NAME>` refuses while a sandbox holds the secret, and names those sandboxes. Ungrant it first, remove those sandboxes, or pass `--force`.

## Grant a secret to a sandbox

`shard create --secret <NAME>` gives the sandbox the placeholder as `$NAME`, and records the grant in the sandbox record. `shard inspect` prints the grants as `secrets`. `shard run` takes `--secret` too.

A secret is granted to destinations, never to a sandbox alone. A request to a host that is not a destination carries the placeholder.

**Caution: grant a secret only to hosts that never send the credential back.** The host puts the value into the request and never reads the response. A granted host that echoes a header it received, such as an echo endpoint or a debug page, returns the real value to the sandbox.

A grant opens no host. The sandbox's policy decides what it can reach, so a sandbox with a policy needs an allow rule for each granted host. A grant does put the sandbox behind the egress proxy, for every host it reaches. A TLS handshake with no server name is then refused, and a request whose `Host` differs from the handshake name gets `400`. See [egress](https://github.com/presmihaylov/shard/blob/main/docs/egress.md).

A fork keeps the grants of its source. A snapshot holds no grant, so a create from a snapshot needs its own `--secret`.

`shard secret grant <sandbox> <NAME>` gives a sandbox the same placeholder that `--secret` gives at create. `shard secret ungrant <sandbox> <NAME>` takes it back. The sandbox reads the change at its next start.

Both commands take only a `created` or `stopped` sandbox. A running sandbox holds its environment in its processes, and a paused one holds it in its checkpoint, so both fail with `stop it first`. A second grant of the same secret changes nothing.

A grant is refused when the sandbox's environment already holds that name. A refused grant changes nothing. A secret named `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `NODE_EXTRA_CA_CERTS` or `CURL_CA_BUNDLE` is refused at create and at a grant, because the proxy sets those variables.

## Where the value goes in

The host puts the value in only when all of these hold:

- the request goes over TLS, on port `443`
- the request goes to a destination of the secret
- the placeholder appears exactly, in a header value

A placeholder in the path, the query or the body goes out unchanged. An upstream can quote those fields back in an error, which would hand the value to the sandbox. Put the key in a header, where every SDK puts it.

Plain HTTP never gets the value, even to a granted host, because it crosses the network in clear text. Send the credential over `https://`.

Only HTTPS on port `443` gets the value. A credential on any other port or protocol, such as a database password on `5432` or SMTP on `587`, leaves as the placeholder. The policy still decides whether the connection is allowed.

HTTP Basic auth works. The host decodes the header, puts the value in and encodes it again, so `https://api:mock-KEY@host` works. Any other encoding or signing of the key gets no value.

A hop-by-hop header keeps the placeholder, because it belongs to the connection, not the upstream. These are `Connection`, `Proxy-Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `Te`, `Trailer`, `Transfer-Encoding`, `Upgrade`, and any header that `Connection` names.

## Choose the placeholder

The placeholder is `mock-<NAME>` by default. An SDK that checks the shape of a key before it sends it never sends `mock-<NAME>`. For such an SDK, give a placeholder of the right shape:

```sh
shard secret set --destination api.stripe.com --placeholder sk_test_placeholder01 STRIPE_KEY
```

A placeholder you choose uses only letters, digits, `_`, `-` and `.`, so no URL, JSON or base64 encoder changes it. It is refused when:

- it is shorter than 8 characters
- it holds any other character
- it is inside the value, or the value is inside it
- another secret owns it, as its own placeholder or as its default

The default `mock-<NAME>` skips the first two checks, so a short name still gets one. It still has to pass the last two.

A placeholder change is refused while a sandbox holds the secret, because that sandbox already holds the old placeholder. Ungrant the secret first.

## Grant a wildcard

```sh
printf '%s' "$GITHUB_TOKEN" | shard secret set --destination '*.github.com' GITHUB_TOKEN
```

`*.github.com` grants the value to every host under `github.com`. The `*` must be the leftmost label, over a domain that someone can register. So `*.github.com` and `*.openai.com` are accepted. `*.*`, `*.com`, `api.github.*`, a bare `*`, and a public suffix such as `*.co.uk` or `*.github.io` are refused.

## Rotate a secret

Run `shard secret set` again with the same name to replace the value. The destinations and the placeholder stay, unless `--destination` or `--placeholder` names new ones. Nothing caches the value: the proxy reads the store on every request, so a running sandbox uses the new value on its next request.

A secret removed with `--force` while a sandbox held it cannot be set again until that sandbox ungrants it. The sandbox keeps the old placeholder, and nothing records it any more. Stop the sandbox, ungrant the secret, set it, and grant it again.

## Clients that do not trust the proxy

The proxy reads HTTPS, so the sandbox must trust its certificate authority. shard adds it to the file the image already reads, and points `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `NODE_EXTRA_CA_CERTS` and `CURL_CA_BUNDLE` at it. OpenSSL, curl, Python, Ruby, PHP, Go, .NET, Node, Deno and Bun read it. Three kinds of client do not.

**Java** trusts its own keystore. `keytool` imports only the first certificate of a file, and the proxy's is the last. In the sandbox, on JDK 9 or later:

```sh
awk '/-BEGIN CERTIFICATE-/{c=""} {c=c $0 "\n"} END{printf "%s", c}' "$SSL_CERT_FILE" > /tmp/shard-proxy-ca.pem
keytool -importcert -noprompt -cacerts -storepass changeit -alias shard-proxy -file /tmp/shard-proxy-ca.pem
```

Or point `-Djavax.net.ssl.trustStore` at a store that holds it. The server keeps the certificate alone at `<root>/proxy/ca.crt`.

**Rust** built with `rustls` and `webpki-roots` compiles its roots in. Build with `rustls-native-certs` instead, which reads the same file.

**A client that pins a certificate or a public key** refuses the proxy. The call fails with a certificate error, and the value never goes out.

## What it stops, and what it does not

A secret keeps the value out of the sandbox. Code in the sandbox can read its environment, dump its memory and search its disk, and it finds only the placeholder. The one way back is a granted host that echoes a header, which is why a grant names only hosts that never do.

On the `runc` provider, the proxy is the only thing between the sandbox and the value. Root in the sandbox is root on the host, and an escape reads the secret store as the host does.

A secret does not stop misuse of the key. A sandbox that can call `api.openai.com` with the key can make any call the key allows. Limit the key at the API provider. shard only keeps the key from leaving.
