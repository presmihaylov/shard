What a server can do depends on its provider. Ask it which lifecycle verbs it supports:

## An unsupported command fails, with no fallback

Sysbox and runc have no `pause`, `resume` or `fork`. There each one fails before it changes anything, and shard never runs a weaker command in its place, such as a stop instead of a pause. For the error and the commands of each provider, see [Providers and capabilities](/docs/concepts/providers/#an-unsupported-command-fails-with-no-fallback).

## Isolation

How far a sandbox is from the host depends on the provider. runc isolates nothing, so use it only for code you trust, and Sysbox sandboxes are not isolated from each other, so run one tenant per Sysbox host. For what each provider puts between a sandbox and the host, see [Isolation by provider](/docs/security/isolation/).

Sysbox and runc also have limits of their own:

- **Sysbox** does not give a sandbox a kernel keyring, so the keyring calls `add_key`, `keyctl` and `request_key` fail with `ENOSYS`. On host kernel 6.12.107 with Sysbox 0.7.1, Docker in the sandbox starts, but every container it runs fails to mount `/sys/fs/cgroup`. On kernel 6.12.101 they run.
- **runc** answers the keyring calls with `EPERM`.

**systemd cannot be a sandbox's PID 1, on any provider.** shard's own supervisor, `shard-init`, is PID 1 in every sandbox, and systemd refuses to manage the system from any other PID. To run systemd, run it inside a Docker container that the sandbox starts.

## Resource bounds

A sandbox can have four bounds: memory, CPU, processes and disk. On `vz` and `firecracker` it also gets a swap file inside its disk.

**Memory.** When a sandbox goes past its `--memory` bound, the whole sandbox ends, not just one process in it, and the daemon starts it again on its own with the files it kept:

- **The record says why.** It says `stopped`, with the reason `ran out of memory and the host ended it`.
- **The wait grows.** The first start runs within 5 seconds. A sandbox that runs out of memory again within 10 minutes of a start waits 10 seconds for the next one, and the wait doubles up to 5 minutes.
- **A stop cancels it.** A `stop` or a `remove` calls off a start that is still due.
- **gVisor has headroom.** The sandbox slows down at 32 MiB over its bound and ends at 64 MiB over it. The host counts gVisor's own memory against the same bound.

`create` refuses these bounds:

- a bound above the server's total memory, on every provider
- a bound from 1 to 127 MiB on `vz` and `firecracker`, where 0 or no `--memory` means 512 MiB
- a bound from 1 to 63 MiB on `gvisor`, where 0 means no bound

**Swap.** On `vz` and `firecracker`, a sandbox gets a swap file of 2 GiB on its own disk unless `--swap` names another size, and `--swap 0` means none. Past its memory bound it swaps instead of ending, and the memory bound still holds the RAM it uses.

`create` refuses a swap that is not smaller than `--disk`, and gVisor, Sysbox and runc refuse any swap above 0.

**CPU.** `create` refuses a `--vcpus` above 32 on Firecracker, and one outside Virtualization.framework's range on `vz`.

**Processes.** A fork bomb stops at 4096 processes on gVisor, Sysbox and runc, well below the host's limit. On Firecracker and vz it stays inside the virtual machine and hits its memory bound.

**Disk.** `--disk` bounds everything a sandbox can write. The default is 10240 MiB, and no value turns the bound off.

A write that would go past the bound fails with `ENOSPC`, and the sandbox keeps running. On Firecracker and vz, a few sizes are refused, and the error names the nearest sizes that work.

For the defaults of each bound on each provider, see [Resource bounds by provider](/docs/concepts/providers/#resource-bounds-by-provider).

## Network

- **Inbound only through a forwarded port.** Nothing outside can open a connection into a sandbox unless `shard port add` forwards a host port to it. A forward carries TCP only, and reaches the program only where it listens on the sandbox's `127.0.0.1` or on every interface.
- **No IPv6.** A sandbox gets one IPv4 address, and the host drops every IPv6 packet it sends.
- **A name rule covers only TCP ports 80 and 443.** For any other port, write an address rule.
- **Names resolve when the rules are applied.** The host resolves each name rule to its addresses when it writes the rules. If a host's addresses change, store the policy again.
- **The log does not record every drop.** A packet dropped by another firewall rule on the server leaves no record. On Linux, the host logs at most 2 drops a second for each rule of a sandbox, with a burst of 10.
- **A client that pins a certificate refuses the proxy.** The proxy reads HTTPS using its own certificate authority. Java, and Rust built with `webpki-roots`, need an extra step to trust it.

For policies and the decision log, see [egress](/docs/security/egress/).

## Secrets

- **Only a header value gets the secret.** The host puts the value in only over TLS on port `443`, to a destination of the secret, and only where the placeholder appears exactly in a header. HTTP Basic auth works. A placeholder in the URL or the body goes out unchanged, and a client that signs a request with the key, instead of sending the key, gets no value.
- **A granted host that echoes a header returns the value.** The host never reads the response, so grant a secret only to hosts that never send the credential back.
- **A secret does not stop misuse of the key.** A sandbox that can call a granted host can make any call the key allows. Limit what the key can do at the API provider.
- **On runc, the proxy is the only barrier.** Code that escapes the sandbox can read the secret store just as the host does.

For how the host guards a secret, see [Secrets](/docs/security/secrets/). To grant one step by step, see [Give a sandbox an API key with credential brokering](/docs/essentials/credential-brokering/).

## The API

- **The socket grants every right.** A request on the daemon's unix socket carries no token and no scopes, so anyone who can open the socket controls every sandbox and every secret on the server.
- **`shard serve` speaks plain HTTP.** Put an HTTPS proxy or a tunnel in front of it before a token crosses a network.
- **A token stays valid until it expires or you revoke it.** A token minted without `--duration` never expires. Nothing rotates the signing key.

For who can reach the socket, see [Who can reach the API](/docs/security/model/#who-can-reach-the-api). For tokens and scopes, see [Authentication](/docs/reference/auth/).

## One server

shard runs sandboxes on one server. It does not spread them across servers, and it does not move a sandbox from one server to another.

A daemon uses one provider for every sandbox on the server. A root stays tied to the provider that made its records, and the daemon refuses a `--provider` that names a different one.

## Pause and fork

- **A gVisor pause that fails partway loses the sandbox.** When a checkpoint begins but does not finish, the sandbox ends and its record says `failed`.
- **An `exec` that runs across a Firecracker fork loses its stream.** It fails with an error, and its command keeps running in the sandbox with nothing reading its output. An `exec` that starts while the fork holds the sandbox frozen is refused. Run it again when the fork returns.

For the other limits of pause and fork, see [Pause, resume and fork](/docs/concepts/pause-resume-fork/#limits-to-know).
