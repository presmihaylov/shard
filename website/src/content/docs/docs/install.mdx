Install the shard CLI with one command, or add an SDK to your project:

<Tabs syncKey="lang">
<TabItem label="CLI">

```sh
curl -fsSL https://useshards.com/install | sh
```

</TabItem>
<TabItem label="TypeScript">

```sh
npm install useshards
```

</TabItem>
<TabItem label="Python">

```sh
pip install useshards
```

</TabItem>
</Tabs>

The installer puts the CLI at `~/.local/bin/shard`. The installer itself needs no root and changes nothing else on the machine. If a terminal is attached, it then offers to start `shard setup`. Setup is the step that changes the machine: it turns this machine into a sandbox host or connects it to a remote shard server.

The TypeScript SDK needs Node.js 20.3 or later, and the Python SDK needs Python 3.11 or later. Both talk to a host through `shard serve`.

## What the installer does

1. Detects the operating system and the CPU architecture.
2. Asks the GitHub releases API for the newest stable shard release, a `vX.Y.Z` tag that is neither a draft nor a prerelease, and prints that version.
3. Downloads this platform's binary and the release's `SHA256SUMS` from that same release into a temporary directory.
4. Verifies the binary's checksum, and stops if it does not match.
5. Checks that the new binary reports the expected version, then moves it over `~/.local/bin/shard`.
6. Prints the install path and, if `~/.local/bin` is not on `PATH`, the line that adds it for new shells and the `export` that adds it to the current one. Under fish, it prints one `fish_add_path` line instead.

An existing `shard` stays in place until the installer has downloaded and verified the new binary. On a failure or an interrupt, the installer removes its temporary files and leaves the old binary as it was.

## Supported platforms

| Platform | Sandbox host | Remote client |
| --- | --- | --- |
| Linux, x86_64 | Yes | Yes |
| macOS, Apple silicon | Yes | Yes |
| macOS, Intel | No | Yes |
| Windows | No | Inside WSL 2 |

A Mac needs macOS 14 or later to host sandboxes. On Windows, run the installer inside WSL 2, where it installs the Linux build. The SDKs need only Node.js or Python, so they connect from Windows as well. On another CPU architecture, the installer stops with an error that lists the builds in the release. Under Rosetta, an Apple silicon Mac gets the native arm64 build.

## Upgrade

On a machine that only connects to a remote server, run the installer again. On a sandbox host, run `shard setup` and choose **Upgrade shard**: setup replaces the CLI and the daemon with the newest release and restarts the daemon, and your sandboxes keep running.

## Uninstall

On a sandbox host, remove your sandboxes, then run `shard setup` and choose **Uninstall shard**. Setup removes what it installed, leaves [your data](#where-shard-keeps-its-state) in place, and prints the commands that remove the rest. On a machine that only connects to a remote server, choose **Remove this connection** in `shard setup`, then delete `~/.local/bin/shard`.

## Where shard keeps its state

A sandbox host keeps its sandboxes, images, snapshots, secrets and network policies in `/var/lib/shard`. On Linux, when the disk under it cannot clone files, that directory is a mount of the disk image `/var/lib/shard.xfs`. On a Mac, the daemon logs to `/var/log/shard`. A remote client keeps its saved connection in `~/.config/shard/config.json`.
