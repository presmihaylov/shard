The installer puts the CLI at `~/.local/bin/shard`. The installer itself needs no root and changes nothing else on the machine. If a terminal is attached, it then offers to start `shard setup`. Setup is the step that changes the machine: it turns this machine into a sandbox host or connects it to a remote shard server.

The TypeScript SDK needs Node.js 20.3 or later, and the Python SDK needs Python 3.11 or later. Both talk to a host through `shard serve`.

## What the installer does

1. Detects the operating system and the CPU architecture.
2. Asks the GitHub releases API for the newest stable shard release, a `vX.Y.Z` tag that is neither a draft nor a prerelease, and prints that version.
3. Downloads this platform's binary and the release's `SHA256SUMS` from that same release into a temporary directory.
4. Verifies the binary's checksum, and stops if it does not match.
5. Checks that the new binary reports the expected version, then moves it over `~/.local/bin/shard`.
6. Prints the install path and, if `~/.local/bin` is not on `PATH`, the line that adds it for new shells and the `export` that adds it to the current one. Under fish, it prints one `fish_add_path` line instead.

An existing `shard` stays in place until the installer has downloaded and verified the new binary. On a failure or an interrupt, the installer removes its temporary files and leaves the old binary as it was.

## Supported platforms

| Platform | Sandbox host | Remote client |
| --- | --- | --- |
| Linux, x86_64 | Yes | Yes |
| macOS, Apple silicon | Yes | Yes |
| macOS, Intel | No | Yes |

A Mac needs macOS 14 or later to host sandboxes. On another CPU architecture, the installer stops with an error that lists the builds in the release. On another operating system, it stops with an error that names the system. On Windows, run it inside WSL 2. Under Rosetta, an Apple silicon Mac gets the native arm64 build.

## Set up later

Without a terminal, for example in CI or under `ssh host 'curl ... | sh'`, the installer skips the prompt and prints:

```text
Set up shard later:
  shard setup

For automated setup:
  shard setup --help
```

## Setup exit codes

`shard setup` ends with one of these codes, so a script can tell the outcomes apart:

| Code | When |
| --- | --- |
| 0 | Setup finished, or there was nothing to do |
| 1 | A check or a step failed, setup refused an option, you declined the confirmation, or setup found a manual installation, which it does not change |
| 130 | You left setup with Ctrl+C. The steps done so far stay in place |

## Install by hand

Setup is the usual way to make a Linux host. To install one without it, first install the host tools and your provider's runtime. Every Linux provider runs `ip`, `nft` and `mkfs.ext4`, from the packages `iproute2`, `nftables` and `e2fsprogs`. The runtime is `runsc` for gVisor, `sysbox-runc` for Sysbox, or `runc`. Firecracker needs more tools, so set it up with [`shard setup`](/docs/guides/kvm/).

The unit starts `shard daemon` with no `--provider`. On a fresh root, the daemon then runs Firecracker when `/dev/kvm` opens, and gVisor when it does not. To pick the provider, add `--provider gvisor`, `--provider sysbox` or `--provider runc` to `ExecStart` in `/etc/systemd/system/shard.service`, after the `install` lines and before `systemctl daemon-reload`. As root:

```sh
base=https://github.com/presmihaylov/shard/releases/latest/download
for f in shard-linux-amd64 shard-init-linux-amd64 shard.service SHA256SUMS; do curl -fsSLO "$base/$f"; done
sha256sum --ignore-missing -c SHA256SUMS
install -m0755 shard-linux-amd64 /usr/local/bin/shard
install -m0755 shard-init-linux-amd64 /usr/local/bin/shard-init
install -m0644 shard.service /etc/systemd/system/shard.service
systemctl daemon-reload
systemctl enable --now shard
```

Without `nft`, the daemon still starts, but every `shard create` fails and the `proxy` and `dns` tasks restart in a loop. Install `nftables` and the next restart of those tasks succeeds, with no restart of the daemon. The daemon looks for the guest supervisor at `/usr/local/bin/shard-init`. To keep it somewhere else, set `SHARD_INIT_PATH` in the unit's environment.

## Upgrade

On a machine that only connects to a remote server, run the installer again. It finds the newest release each time and replaces `~/.local/bin/shard` in place.

On a sandbox host, run `shard setup`, choose **Run sandboxes on this machine**, then **Upgrade shard**. The daemon runs the copy that setup installed in `/usr/local/bin`, so the installer alone does not upgrade it. Setup downloads and verifies the new release before it replaces anything. It replaces `/usr/local/bin/shard`, `/usr/local/bin/shard-init` on Linux, and the `shard` you ran it from, and keeps the provider. If the installed version is already the newest, setup says so and changes nothing.

Setup tells you before it restarts the daemon. A running background service restarts on the new version, and the upgrade waits until the daemon answers. Your sandboxes keep running while the daemon restarts. Open `shard exec` and `shard shell` sessions disconnect, and their commands keep running. If you start the daemon yourself, restart `shard daemon` after the upgrade.

## Uninstall

On a sandbox host, remove your sandboxes first. Then run `shard setup`, choose **Run sandboxes on this machine**, then **Uninstall shard**. If any sandbox is left, uninstall refuses and prints the commands that list and remove sandboxes.

Uninstall stops and removes the background service, removes the files that setup installed, and on Linux removes the network bridge, its firewall tables and the rules that let it through `ufw` or `firewalld` when the bridge has no port and nothing listens on the proxy ports. Your data in `/var/lib/shard` stays, and so do tools that other software may also use. The closing note names what stays, and the command that removes each of these: the data in `/var/lib/shard`, on Linux the `/var/lib/shard.xfs` disk image, its lock file and its `/etc/fstab` line, on a Mac the daemon logs in `/var/log/shard`, each shared tool that setup installed, and every `shard` command that is left. The command that removes the `/etc/fstab` line ends with `systemctl daemon-reload`, so systemd also drops the mount it made from that line. If the disk image is gone but its `/etc/fstab` line stays, the note says so, because that line would fail its mount at every boot. Uninstall never turns IP forwarding off. On Linux, if the bridge stays, the note says so. Otherwise, if forwarding is on, the note prints the command that turns it off.

On a machine that only connects to a remote server, run `shard setup`. If a connection is saved, the first screen names the server: choose **Remove this connection**. Then remove the CLI:

```sh
rm ~/.local/bin/shard
```

## Output

The banner uses color when standard output is a terminal. Set `NO_COLOR` to turn the color off. The installer takes no options.

## Troubleshooting

The installer makes one unauthenticated call to the GitHub API, which allows 60 calls an hour for each IP address. When you reach that limit, the installer stops with an error that says so. Run it again an hour later. The installer never falls back to a fixed version.
