A sandbox keeps its files across a stop, and its memory and processes too across a pause.

Create a sandbox, write a file, stop it, start it again, pause it and resume it:

<Tabs syncKey="lang">
	<TabItem label="CLI">

```sh
shard create --name demo --memory 512MiB alpine:3.20
shard exec demo sh -c 'echo hello > /root/hello.txt'
shard stop demo
shard start demo
# Prints hello: the stop kept the file.
shard exec demo cat /root/hello.txt
shard pause demo
shard resume demo
shard remove --force demo
```

	</TabItem>
	<TabItem label="TypeScript">

```ts
import { Shard } from "useshards";

const shard = new Shard();
const sandbox = await shard.create({ name: "demo", image: "docker.io/library/alpine:3", memoryMiB: 512 });
try {
  await sandbox.exec(["sh", "-c", "echo hello > /root/hello.txt"]);
  await sandbox.stop();
  await sandbox.start();
  // Prints hello: the stop kept the file.
  console.log((await sandbox.exec(["cat", "/root/hello.txt"])).stdout);
  await sandbox.pause();
  await sandbox.resume();
  console.log((await sandbox.inspect()).state); // running
} finally {
  await sandbox.remove({ force: true });
  shard.close();
}
```

The file is still there after the start, because a stop keeps the sandbox's files. A stop and a pause both free the sandbox's memory, but only a pause brings the processes back:

| | `stop`, then `start` | `pause`, then `resume` |
| --- | --- | --- |
| Files | Kept | Kept |
| Memory and processes | Lost. A process whose restart policy allows it starts again from the beginning. | Saved to disk. The processes carry on where they left off. |
| Providers | Every provider | gVisor, Firecracker, and macOS Virtualization on Apple silicon with macOS 14 or later. Sysbox and runc refuse them. |

## The states

A sandbox is always in one of seven states.

| State | What it means |
| --- | --- |
| `pending` | The image is still downloading, or the sandbox is still starting. Every create begins here. |
| `running` | The sandbox is up, and you can run commands in it. |
| `paused` | The memory and the processes are saved on disk, so the sandbox uses no memory. |
| `stopped` | The processes have ended, but the files are kept. `start` runs the sandbox again. |
| `unresponsive` | The sandbox runs, but its virtual machine process did not answer a health check. This state exists only on macOS Virtualization and Firecracker. |
| `failed` | A create, a fork or a pause lost the sandbox. Only `remove` frees it. |
| `created` | The new copy from a fork, for a moment before it runs. No command leaves a sandbox in this state. |

## What each command does

### `create`

`create` puts the sandbox in `pending`, and the CLI and both SDKs wait until it is `running` or `failed`. While it waits, the CLI shows the download on stderr.

A new sandbox has no processes. Only shard's own supervisor runs in it. `shard run` starts a named process in it, and `exec` runs a one-off command.

### `stop`

`stop` sends SIGTERM to the sandbox's processes, gives them 30 seconds to exit, then kills them. The files stay on disk.

- The 30 seconds are fixed.
- `stop` succeeds only once the processes have ended. If the provider still reports a live process after 5 more seconds, the stop fails and the state does not change.
- A `stop` on a `pending` sandbox cancels the create. The sandbox becomes `failed` with the reason `the create was cancelled by shard stop`.

### `start`

`start` runs a `stopped` sandbox again, with the files the stop kept. Memory, processes and open sockets were lost at the stop.

A process with the `always` restart policy starts again from the beginning, and so does an `unless-stopped` one that `shard kill` did not end.

### `pause`

`pause` saves the memory and the processes to disk and frees the memory.

A `pause` ends any `exec` that is still running. An `exec` on a paused sandbox fails with `sandbox <name> is paused: resume it with shard resume <name>`.

### `resume`

`resume` continues a `paused` sandbox from its checkpoint, and the processes carry on where they left off.

### `fork`

`fork` freezes a `running` sandbox, copies its memory and files into a new sandbox, then lets the source continue. The new sandbox goes from `created` to `running`.

- Fork works only on a `running` sandbox, and on the same providers as pause.
- On gVisor the copy has a 10-minute limit. Past it, the fork fails and shard tries to resume the source.

### `snapshot create`

`snapshot create` copies the files of a `stopped` sandbox, and the sandbox stays `stopped`. A snapshot is not a sandbox and has no state.

On a running or paused sandbox it fails with `409 sandbox_not_stopped`, because such a sandbox holds memory that a copy of its files would miss.

### `remove`

`remove` deletes the sandbox and its files.

- It refuses a `running` or `paused` sandbox unless you pass `--force`. Then it stops the sandbox first, with the same 30 seconds.
- A `pending` sandbox needs no `--force`: the remove cancels its download.

## failed is terminal

A `failed` sandbox refuses every command except `inspect` and `remove`. It answers `409 sandbox_failed` with the reason. Read the reason, then remove the sandbox.

A sandbox becomes `failed` when:

- The image download or the start failed.
- A `stop` cancelled the create.
- The daemon restarted before a create or a fork finished.
- A gVisor `pause` began its checkpoint but did not finish. Nothing is left to resume.

## unresponsive

On macOS Virtualization and Firecracker, each sandbox is a virtual machine process on the host. The daemon checks that this process answers, within 5 seconds on macOS Virtualization and within 4 seconds on Firecracker. If the process stays silent for that whole time, the sandbox becomes `unresponsive`. A host under heavy load can cause that, and so can a SIGSTOP.

shard does not end an `unresponsive` sandbox because it is silent. The process can come back with the same virtual machine, and when it answers, the sandbox is `running` again. Until then, `exec`, `start` and `pause` refuse it, and `exec` says `wait for it to answer, or end it with shard stop <id>`. `stop` and `remove --force` give it one more second to answer, then kill it.

If the process dies, the sandbox becomes `stopped`. If a `pause` wrote its checkpoint before the process died, the sandbox becomes `paused` with that checkpoint instead.

## When the daemon restarts

A sandbox that already runs does not depend on the daemon. When the daemon stops or restarts, running sandboxes continue, and the next daemon picks them up again. The next daemon also corrects what the last one left behind:

- A `running` sandbox with no process behind it becomes `stopped`, with the reason `daemon restarted and found no process`.
- A `paused` sandbox with no checkpoint becomes `stopped`.
- A create in progress becomes `failed`, with the reason `the daemon restarted before the create finished`.
- A fork copy in progress becomes `failed`, with the reason `the daemon restarted before the fork finished`.
