The data directory is where the daemon keeps everything it manages: the sandboxes, the images, the snapshots, the secrets and the network policies. It is `/var/lib/shard`, and `shard setup` creates it. To use another directory, start the daemon with `shard --root <dir> daemon` and pass the same `--root` to every command.

- **The daemon is its only writer.** Every command goes to the daemon, and the daemon changes the files. Nothing else writes there.
- **One daemon per data directory.** The daemon holds a lock on `daemon.lock`, so a second daemon on the same directory refuses to start.
- **One provider per data directory.** Each sandbox record names the provider that made it. A daemon refuses to start on a data directory that holds another provider's sandboxes, because it cannot run them.
- **Commands find the daemon through it.** A command on the host connects to the socket `shard.sock` in the data directory.

## What it holds

### Sandboxes

- **`sandboxes/<id>/`**: one directory per sandbox. It holds the record, `sandbox.json`, with the sandbox's name, state, provider, image and bounds, as well as its logs and the files its provider runs it from.
- **`names/`**: one link per sandbox name, to that sandbox's directory.
- **`checkpoints/`**: the saved memory of each paused sandbox.
- **`network/leases/`**: one file per IP address a sandbox holds on the sandbox network.

### Images and snapshots

- **`images/layout/`**: every pulled image, as an OCI image layout.
- **`images/rootfs/`**: each image unpacked into a directory, one per image digest, so two tags of one image unpack once.
- **`images/erofs/`**: on Firecracker, each image as a read-only EROFS file that a microVM boots from.
- **`images/disks/`**: on vz, each image as an ext4 disk that a virtual machine boots from.
- **`snapshots/<id>/`**: one directory per snapshot, with its record, `snapshot.json`, and the files it copied from the sandbox.
- **`snapshot-names/`**: one link per snapshot name.

### Secrets and network policies

- **`secrets/`**: one file per secret, with mode `0600`. This is the only place a secret value is written.
- **`policies/`**: the network policies.
- **`proxy/`**: the certificate authority of the egress proxy.
- **`egress.cursor`**: where the daemon left off in the kernel log, so a restart can still log the packets the host dropped while the daemon was down.

### The daemon

- **`shard.sock`**: the API socket.
- **`daemon.lock`** and **`daemon.pid`**: the lock that keeps one daemon on the directory, and that daemon's process ID.
- **`auth/`**: the signing key and the token ledger of `shard serve`. On a Mac, also the API key that setup made.
- **`.reserve`**: 64 MiB held back, so the daemon can start on a full disk and serve the `remove` that frees space.

### The provider

Only the provider in use makes its own paths:

- **`runsc/`, `runc/` and `sysbox-runc/`**: the runtime's state for each sandbox, on gVisor, runc and Sysbox.
- **`exec/`**: the scratch files of each running `exec`, on gVisor, runc and Sysbox. The daemon clears what an earlier daemon left when it starts.
- **`firecracker/`** and **`jail/`**: on Firecracker, each microVM's files, and the jail the jailer starts it in.
- **`vz/`**: on a Mac, the helper that runs each virtual machine, and the guest's `shard-init`. The daemon installs both from its own binary.
- **`kernel/`**: the guest kernel for Firecracker and vz, which the daemon downloads when it first starts.

## Outside the data directory

shard also puts a few things elsewhere on a sandbox host:

- **`/usr/local/bin/shard`**, and on Linux **`/usr/local/bin/shard-init`**: the binaries that setup installs.
- **The service:** `/etc/systemd/system/shard.service` on Linux, or `/Library/LaunchDaemons/shard.daemon.plist` on a Mac.
- **The API key:** `/etc/shard/api-key` on Linux, when setup serves the HTTP API.
- **`/var/log/shard`**: the daemon's logs on a Mac. On Linux, the logs go to the journal.
- **`/var/run/shard/host.lock`**: on Linux, the lock that keeps a second daemon off the host, because every data directory shares one sandbox network.
- **The sandbox network:** on Linux, the bridge `shard0`, one `veth` pair per running sandbox, and the nft tables `inet shard` and `bridge shard`. On a host that runs firewalld, a `shard` zone holds the bridge.
- **`/var/lib/shard.xfs`**: on Firecracker, when the filesystem under `/var/lib/shard` cannot clone files, an XFS image mounted over `/var/lib/shard`, with its line in `/etc/fstab`.

A machine that only connects to a remote server keeps the CLI at `~/.local/bin/shard` and the saved connection in `~/.config/shard/config.json`.
