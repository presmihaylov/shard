Pause frees a sandbox's memory on the host, and resume carries its processes on where they left off. Fork turns one prepared sandbox into as many as you need, without setting each one up again.

Pause a sandbox, resume it, then fork it into a second sandbox with files of its own:

<Tabs syncKey="lang">
<TabItem label="CLI">

```sh
shard create --name demo --memory 512MiB alpine:3.20
shard exec demo sh -c 'echo before > /root/state.txt'
shard pause demo
shard resume demo
shard fork --name demo-copy demo
shard exec demo-copy sh -c 'echo copy > /root/state.txt'
shard exec demo cat /root/state.txt
shard remove --force demo-copy
shard remove --force demo
```

</TabItem>
<TabItem label="TypeScript">

```ts
import { Shard } from "useshards";

const shard = new Shard();
try {
  const sandbox = await shard.create({ image: "alpine:3.20", name: "demo", memoryMiB: 512 });
  try {
    await sandbox.files.write("/root/state.txt", "before\n");
    await sandbox.pause();
    await sandbox.resume();

    const copy = await sandbox.fork({ name: "demo-copy" });
    try {
      await copy.files.write("/root/state.txt", "copy\n");
      process.stdout.write((await sandbox.exec("cat /root/state.txt")).stdout);
    } finally {
      await copy.remove({ force: true });
    }
  } finally {
    await sandbox.remove({ force: true });
  }
} finally {
  shard.close();
}
```

Each version prints `before`, because the write in `demo-copy` changed only its own files.

The example needs a host that runs `gvisor`, `firecracker` or `vz`. The SDKs connect to `shard serve` at the URL in `SHARD_REMOTE`, with the key in `SHARD_API_KEY`.

## Pause and resume

`shard pause` saves a running sandbox's memory and files to a checkpoint on disk, then ends its processes. A paused sandbox uses no memory on the host. Its state is `paused`, and it keeps its record, its files and its address.

`shard resume` restores a paused sandbox from its checkpoint. Its processes carry on where they left off, and it keeps the same address. shard applies the sandbox's network rules again on each resume.

## Fork

`shard fork` works on a running sandbox. The source freezes for a moment while shard captures its memory and files, then keeps running. The new sandbox starts from that capture, in the `running` state. The command prints the new sandbox's ID.

The new sandbox has its own ID, its own address and its own files. A write in one sandbox never shows in the other. The new sandbox keeps the source's image, resource limits, granted secrets, network policy and processes, with their restart policies. Give it a name with `--name`.

To keep a pool of warm sandboxes, prepare one sandbox, then fork it once for each sandbox you need. Each fork starts with the processes and the files that the source had.

## Limits to know

- **A pause ends running commands.** Any `exec` still running in the sandbox ends. While the sandbox is paused, `shard exec` runs nothing and fails with `sandbox demo is paused: resume it with shard resume demo`.
- **A pause can take up to 10 minutes.** A client that disconnects does not cut it short, because the sandbox would not survive a partial checkpoint. If a pause fails, the error says why, and `shard inspect demo` shows the state that shard found.
- **A stop deletes the checkpoint.** `shard stop` on a paused sandbox ends it, so you can no longer resume it. Its files stay, and `shard start` runs it again from them, with new memory.
- **A daemon restart keeps the pause.** A paused sandbox stays paused when the daemon restarts, as long as its checkpoint is on disk. If its checkpoint is gone, it becomes `stopped`.
- **A fork starts with empty logs.** It also does not get the source's port forwards.
- **A Firecracker fork needs XFS or Btrfs.** The fork shares the sandbox's disk blocks. On any other filesystem, the daemon puts its data directory on an XFS image. See [the data directory](/docs/quickstart/server/#the-data-directory).

## Fork or snapshot

A snapshot also copies a sandbox, but only its files:

| | Fork | Snapshot |
| --- | --- | --- |
| Source | A running sandbox | A stopped sandbox |
| Copies | Memory and files | Files only |
| Result | A running sandbox | A snapshot, which outlives its source |
| Make a sandbox | `shard fork` makes it | `shard create --snapshot <name>` makes one from it |
| Providers | `gvisor`, `firecracker`, `vz` | Every provider |

```sh
shard stop demo
shard snapshot create --name demo-files demo
shard create --name demo-from-files --memory 512MiB --snapshot demo-files
```

A sandbox made from a snapshot starts like a new sandbox, with the snapshot's files and none of the source's memory.

## Which providers support it

| Provider | `pause`, `resume`, `fork` |
| --- | --- |
| `gvisor` | Yes |
| `firecracker` | Yes |
| `vz` | Yes, on Apple silicon with macOS 14 or later |
| `sysbox` | No |
| `runc` | No |

On a provider that lacks them, each verb fails before it changes anything, with an error that names the provider and the verb, such as `provider sysbox does not support pause on this host; use a server that supports pause`.

To see what the provider of your server supports, run `shard capabilities`. It lists all nine verbs and swap, and marks each one `true` or `false`.
