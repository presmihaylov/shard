A provider is the mechanism that runs and isolates each sandbox. shard has five:

| Provider | Each sandbox is | Host |
| --- | --- | --- |
| `gvisor` | a container behind gVisor, a kernel that runs in user space | Linux |
| `firecracker` | a microVM | Linux with `/dev/kvm` |
| `vz` | a virtual machine on Apple's Virtualization framework | Apple silicon Mac, macOS 14 or later |
| `sysbox` | a Linux container with its own user namespace | Linux, one tenant per host |
| `runc` | a plain Linux container on the host kernel, with no user namespace | Linux, trusted code only |

A daemon runs one provider, and every sandbox on that host runs on it. Each sandbox record names the provider that created it. A [data directory](/docs/concepts/data-directory/) that already holds records refuses any other provider, because that provider cannot read those sandboxes.

To compare the providers for your workload, see [What provider should I pick?](/docs/choose-provider/).

## How a host picks its provider

`shard setup` asks which provider to use, and on Linux the service it installs starts the daemon with `--provider`. Only a daemon started without `--provider` picks one itself. It looks at the data directory first and at the host second:

| The data directory and the host | Provider | Reason |
| --- | --- | --- |
| holds records | the one that made them | `it made the records under <root>` |
| empty, beside a `<root>.xfs` image | `firecracker` | `it made the data image <root>.xfs` |
| empty, on Linux, `/dev/kvm` opens | `firecracker` | `/dev/kvm opens` |
| empty, on Linux, no `/dev/kvm` | `gvisor` | `no /dev/kvm` |
| empty, on Linux, `/dev/kvm` does not open | `gvisor` | `/dev/kvm does not open: <error>` |
| empty, on macOS | `vz` | `macOS runs virtual machines through Virtualization.framework` |

The daemon never chooses Sysbox or runc for you. It runs one of them only when `--provider` names it, or when the data directory already holds records that this provider made.

`shard info` prints the provider and the reason from this table. It does not need a running daemon, so it shows what a daemon started now without `--provider` would run. `shard daemon status` shows the provider of the daemon that is already running. The two differ when that daemon was started with `--provider`. Both commands run only on the server.

## The ten capabilities

Every provider supports `create`, `start`, `stop`, `remove`, `snapshot` and `port`, as well as `exec`, `logs` and `inspect`. Three commands, `pause`, `resume` and `fork`, are optional, because the provider has to save a running sandbox's memory to support them.

| Command | gVisor | Firecracker | vz | Sysbox | runc |
| --- | --- | --- | --- | --- | --- |
| `create`, `start`, `stop`, `remove`, `snapshot`, `port` | yes | yes | yes | yes | yes |
| `pause`, `resume`, `fork` | yes | yes | yes | no | no |

Ask a server what it supports before you build on `pause`, `resume` or `fork`:

`shard capabilities` marks each of the ten `true` or `false`, and `--format json` prints the same ten keys as JSON. The answer depends only on the server's provider, not on your API key's scopes or the state of your sandboxes.

## How each command works

gVisor, Sysbox and runc run each sandbox as a container on the host. Firecracker and vz boot a virtual machine for it. A command does the same thing on every provider, by different means on the host.

### create

`create` pulls the image, gives the sandbox an address on the sandbox network, builds its filesystem and starts it, with `shard-init` as PID 1. On gVisor, Sysbox and runc, each image is unpacked once into the [data directory](/docs/concepts/data-directory/), and every sandbox mounts it read-only as the lower layer of an overlayfs. The sandbox's writes go to the upper layer, on a disk of its own: a sparse ext4 file, sized by `--disk` and mounted over a loop device. On Firecracker, the microVM boots from the image as a read-only EROFS disk, with a second, writable ext4 disk for its writes, and runs inside a jail with its own user and cgroup. On vz, the daemon clones the image's ext4 disk, which APFS does without copying a block, and grows the clone to `--disk`.

### start

`start` runs a stopped sandbox again, from the files its stop kept. On gVisor, Sysbox and runc, the daemon mounts the sandbox's disk and overlay again and creates the container afresh, in a new cgroup. On Firecracker and vz, the virtual machine boots again from the same disks. The sandbox keeps its address, and its processes start from scratch.

### stop

`stop` sends SIGTERM to the sandbox's processes, waits up to 30 seconds, then kills what is left. On gVisor, Sysbox and runc, the daemon then unmounts the overlay and the disk. On Firecracker and vz, `shard-init` passes the SIGTERM on and powers the virtual machine off. The writable layer stays on the host, and so do the record and the address. A stop also deletes the checkpoint of a paused sandbox.

### remove

`remove` closes the sandbox's host ports, removes its container or virtual machine, and frees its address on the sandbox network. Then it deletes the sandbox's record, its disk and any checkpoint, and rewrites the host's network rules. A running or paused sandbox needs `--force`.

### snapshot

`snapshot create` copies the writable layer of a stopped sandbox into the data directory. On gVisor, Sysbox and runc, it copies the overlay's upper layer file by file, with the deletions it records. On Firecracker, it reflinks the writable disk, so the snapshot shares the disk's blocks until either one changes. On vz, it clones the disk the same way on APFS. A snapshot holds no copy of the image: `create --snapshot` lays the files over the same image again, so that image must still be on the host, at the same digest.

### port

`port` opens a listener in the daemon, on `127.0.0.1`, or on every interface with `--public`. The daemon carries each connection to the port on the sandbox's loopback: on gVisor through `runsc port-forward`, on Sysbox and runc from inside the sandbox's network namespace, and on Firecracker and vz over a vsock stream to `shard-init`.

### pause

`pause` saves a running sandbox's memory to a checkpoint in the data directory, then ends its processes, so the sandbox holds no memory on the host. On gVisor, `runsc checkpoint` writes the memory of the sandbox's kernel and processes, and the writable layer stays where it is. On Firecracker, `shard-init` freezes the guest's filesystem, Firecracker pauses the microVM and writes its state and memory to files, and the writable disk is reflinked beside them. On vz, Virtualization.framework saves the machine state, and the disk is cloned beside it.

### resume

`resume` restores a paused sandbox from its checkpoint, at the same address, and applies its network rules again. On gVisor, `runsc restore` loads the memory over the remounted layer. On Firecracker, a new jailed Firecracker process loads the snapshot, and the guest's random number generator gets a new seed, so no two restores of one checkpoint draw the same numbers. On vz, the cloned disk goes back in place, and the virtual machine restores from the saved state.

### fork

`fork` captures a running sandbox and restores the capture as a new sandbox. The source freezes only for the capture, then runs on. On gVisor, `runsc checkpoint --leave-running` saves the memory, and the writable layer is copied onto the new sandbox's own disk. On Firecracker and vz, the daemon snapshots the virtual machine as a pause does, reflinks or clones its disk, and restores the copy with a new address. The new sandbox gets its own record and address, and its logs start empty.

## Refuse, never downgrade

A command that the provider does not support fails immediately, with an error that names the provider and the command:

```text
shard: provider sysbox does not support pause on this host; use a server that supports pause
```

The API answers with status `409` and the code `unsupported`. The TypeScript and Python SDKs throw `UnsupportedError`.

## Resource bounds by provider

`--memory`, `--vcpus` and `--disk` bound a sandbox on every provider, and `--swap` adds a swap file on Firecracker and vz. What each bound does depends on the provider:

| Bound | gVisor | Firecracker | vz | Sysbox and runc |
| --- | --- | --- | --- | --- |
| `--memory` | default no bound, at least 64 MiB | default 512 MiB, at least 128 MiB | default 512 MiB, at least 128 MiB | default no bound |
| `--vcpus` | a CPU time quota | virtual CPUs, at most 32 | virtual CPUs | a CPU time quota |
| `--disk` | default 10 GiB | default 10 GiB | default 10 GiB | default 10 GiB |
| `--swap` | refused above 0 | default 2 GiB, inside `--disk` | default 2 GiB, inside `--disk` | refused above 0 |
| Processes | at most 4096 | no bound | no bound | at most 4096 |

**Memory.** When a sandbox goes past its memory bound, the whole sandbox ends, not just one process in it. It becomes `stopped` with the reason `ran out of memory and the host ended it`, and the daemon then starts it again on its own. On gVisor, the sandbox slows down when it reaches the bound and ends only once it is a little above it. `create` refuses a bound above the host's total memory.

**CPU.** `--vcpus` accepts a non-negative whole number. On gVisor, Sysbox and runc, `0` sets no CPU-time quota. On Firecracker and `vz`, `0` gives the VM as many CPUs as the host and provider allow; Firecracker uses at most 32, and `vz` follows Virtualization.framework's range. Firecracker refuses a count above 32, and `vz` refuses a count outside its allowed range.

**Disk.** The bound covers everything the sandbox writes. A write past it fails with `ENOSPC`, but the sandbox keeps running. `--disk 0` means the default size. The disk is sparse, so an unused sandbox takes no space on the host.

**Swap.** On Firecracker and vz, the guest makes a swap file on its own disk at each boot, 2 GiB unless `--swap` names another size. A sandbox past its memory bound then swaps and slows down instead of ending, and it ends only once the swap is full too. The file comes out of `--disk`, so `create` refuses a swap that is not smaller than the disk. `--swap 0` means no swap. gVisor, Sysbox and runc run on the host kernel, so they refuse any `--swap` above 0.

**Processes.** On gVisor, Sysbox and runc, a sandbox can hold at most 4096 processes, and this limit is fixed. In a Firecracker or vz sandbox, processes run inside the virtual machine, so a fork bomb stays inside it and hits the virtual machine's memory.
