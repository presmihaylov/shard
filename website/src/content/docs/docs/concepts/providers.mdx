On a server that runs Sysbox or runc, the CLI prints:

```text
CAPABILITY   SUPPORTED
create       true
start        true
stop         true
remove       true
pause        false
resume       false
fork         false
snapshot     true
```

The answer depends only on the server's provider. Your API key's scopes and the state of your sandboxes do not change it. `shard capabilities --format json` prints the same eight keys as JSON.

## What a provider is

A provider is the mechanism that runs and isolates each sandbox. shard has five:

| Provider | Each sandbox is | Host |
| --- | --- | --- |
| `gvisor` | a container behind gVisor, a kernel that runs in user space | Linux |
| `firecracker` | a microVM | Linux with `/dev/kvm` |
| `vz` | a virtual machine on Apple's Virtualization framework | Apple silicon Mac, macOS 14 or later |
| `sysbox` | a Linux container with its own user namespace | Linux, one tenant per host |
| `runc` | a plain Linux container on the host kernel, with no isolation | Linux, trusted code only |

One daemon runs one provider, and every sandbox on that host runs on it. Each sandbox record names the provider that made it. A data directory that holds records refuses any other provider, because the other provider cannot read those sandboxes.

To compare the providers for your workload, see [the provider matrix](https://github.com/presmihaylov/shard/blob/main/docs/provider.md#the-substrates).

## How a host picks its provider

`shard setup` asks for a provider. On Linux, the service it installs starts the daemon with `--provider`. A daemon started without `--provider` picks one itself. The data directory decides first, and the host decides second:

| The data directory and the host | Provider | Reason |
| --- | --- | --- |
| holds records | the one that made them | `it made the records under <root>` |
| empty, beside a `<root>.xfs` image | `firecracker` | `it made the data image <root>.xfs` |
| empty, on Linux, `/dev/kvm` opens | `firecracker` | `/dev/kvm opens` |
| empty, on Linux, no `/dev/kvm` | `gvisor` | `no /dev/kvm` |
| empty, on Linux, `/dev/kvm` does not open | `gvisor` | `/dev/kvm does not open: <error>` |
| empty, on macOS | `vz` | `macOS runs virtual machines through Virtualization.framework` |

Sysbox and runc are never picked for you. Only `--provider`, or records they already made, can name either one.

`shard info` prints the provider and the reason. It works without a running daemon, so it tells you what a daemon started now without `--provider` would run:

```text
$ shard info
FIELD      VALUE
provider   firecracker
reason     /dev/kvm opens
```

`shard daemon status` shows the provider of the daemon that already runs. The two differ when that daemon was started with `--provider`. Both commands run only on the server.

## The eight capabilities

Every provider supports `create`, `start`, `stop`, `remove` and `snapshot`, and also `exec`, `logs` and `inspect`. Three commands are optional, because they need the provider to save a running sandbox's memory: `pause`, `resume` and `fork`.

| Command | gVisor | Firecracker | vz | Sysbox | runc |
| --- | --- | --- | --- | --- | --- |
| `create`, `start`, `stop`, `remove`, `snapshot` | yes | yes | yes | yes | yes |
| `pause`, `resume`, `fork` | yes | yes | yes | no | no |

Sysbox has none of the three, because `sysbox-runc` has no checkpoint. shard drives no checkpoint on runc either. `vz` needs macOS 14 or later on Apple silicon for all three: a daemon on an older Mac refuses them.

`snapshot` works everywhere, because it copies the files of a stopped sandbox and needs no memory.

## Refuse, never downgrade

A command the provider lacks fails at once. The error names the provider and the command:

```text
shard: provider sysbox does not support pause on this host; use a server that supports pause
```

The API answers with status `409` and the code `unsupported`. The TypeScript and Python SDKs throw `UnsupportedError`.

shard never falls back to a weaker mechanism. A `pause` on Sysbox does not stop the sandbox instead: it fails, and the sandbox keeps running. The daemon checks the capability before it touches the sandbox, so a refusal changes nothing.

Check `shard capabilities` before you build on `pause`, `resume` or `fork`.

## Resource bounds by provider

`--memory`, `--vcpus` and `--disk` bound a sandbox on every provider. What a bound does depends on the provider:

| Bound | gVisor | Firecracker | vz | Sysbox and runc |
| --- | --- | --- | --- | --- |
| `--memory` | optional, at least 64 MiB | required, at least 128 MiB | required, at least 128 MiB | optional |
| `--vcpus` | a CPU time quota | virtual CPUs, at most 32 | virtual CPUs | a CPU time quota |
| `--disk` | default 10 GiB | default 10 GiB | default 10 GiB | default 10 GiB |
| Processes | at most 4096 | no bound | no bound | at most 4096 |

**Memory.** A sandbox past its memory bound ends as a whole, not one process in it. It becomes `stopped` with the reason `ran out of memory and the host ended it`. On gVisor, the sandbox slows down at the bound and ends only a little above it. `create` refuses a bound above the host's total memory.

**CPU.** `--vcpus 0`, the default, sets no bound. On Firecracker and vz, `0` gives the virtual machine one virtual CPU for each host CPU. `create` refuses a fraction such as `0.5` and a count above the host's CPUs.

**Disk.** The bound covers everything the sandbox writes. A write past it fails with `ENOSPC`, and the sandbox keeps running. `--disk 0` means the default. The disk is sparse, so an unused sandbox costs the host no space.

**Processes.** On gVisor, Sysbox and runc, a sandbox holds at most 4096 processes, and nothing changes that. A process in a Firecracker or vz sandbox is a process inside the virtual machine, so a fork bomb stays there and hits the virtual machine's memory.
