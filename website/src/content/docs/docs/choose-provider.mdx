---
title: What provider should I pick?
description: Pick the isolation technology for a shard daemon, from Firecracker, gVisor, vz, Sysbox and runc.
---

The provider is the technology that isolates each sandbox. A daemon runs one provider, and switching later means removing every sandbox, so pick it before you create any.

Run `shard info` on the machine that will be your sandbox host. It prints the provider that a daemon on this host uses by default, and the reason:

```sh
shard info
```

```text
FIELD      VALUE
provider   firecracker
reason     /dev/kvm opens
```

`shard info` inspects the host, not the daemon, so it works before setup.

`shard setup` asks which provider to use, and the cursor starts on the one it recommends. To skip the question, pass the provider:

```sh
shard setup --local --provider gvisor --start-at-boot=true -y
```

## The short answer

| Your host | Pick |
| --- | --- |
| Linux, and `/dev/kvm` opens | `firecracker` |
| Linux without `/dev/kvm` | `gvisor` |
| An Apple silicon Mac with macOS 14 or later | `vz` |
| Linux, one tenant, and the workload runs Docker inside the sandbox | `sysbox` |
| Linux, one tenant, and you trust the code | `runc` |

Setup recommends the first of `vz`, `firecracker` and `gvisor` that runs on the host. It never recommends `sysbox` or `runc`.

## What each provider does

- **`firecracker`**: each sandbox is a microVM with a Linux kernel of its own, on KVM. Use it on any Linux host where `/dev/kvm` opens.
- **`gvisor`**: a kernel in user space, `runsc`, answers the sandbox's system calls, so they never reach the host kernel. Use it on Linux without KVM, such as a cloud VM without nested virtualization.
- **`vz`**: each sandbox is a Linux VM, through Apple's Virtualization.framework. Use it on an Apple silicon Mac.
- **`sysbox`**: a container on the host kernel, with a user namespace and its own `/proc` and `/sys`, so Docker runs inside it. Use it when the workload needs Docker and the host serves one tenant.
- **`runc`**: a plain container on the host kernel, with no user namespace. Use it only for code you trust, on a host with one tenant.

## Compare the providers

| | `firecracker` | `gvisor` | `vz` | `sysbox` | `runc` |
| --- | --- | --- | --- | --- | --- |
| Isolation | A microVM per sandbox | A user-space kernel, `runsc` | A VM per sandbox, through Virtualization.framework | `sysbox-runc`, with a user namespace and virtualized `/proc` and `/sys` | The host kernel, with no user namespace |
| Host | Linux x86_64 with `/dev/kvm` | Linux x86_64 | Apple silicon, macOS 14 or later | Linux x86_64 | Linux x86_64 |
| File-heavy work (`npm install`, `git clone`) | Near native | Slower | Near native | Near native | Near native |
| Docker inside | Yes | No | Yes | Yes | No |
| Tenants on one host | Many | Many | Many | One | One, and only code you trust |
| `pause`, `resume`, `fork` | Yes | Yes | Yes | No | No |

A verb that the provider does not support fails with an error that names the provider and the verb, for example `provider sysbox does not support pause on this host; use a server that supports pause`. shard never falls back to a weaker mechanism. `shard capabilities` lists all nine verbs and swap, and says whether the provider of the server you are connected to supports each one.

## What setup installs

Setup installs what the provider needs, unless the host already has it where the root daemon looks:

| Provider | Setup installs |
| --- | --- |
| `firecracker` | `firecracker` and `jailer` from a pinned release, `erofs-utils` and `xfsprogs` |
| `gvisor` | `runsc` from a pinned gVisor release |
| `sysbox` | The Sysbox CE package from a pinned release |
| `runc` | The `runc` package, and `apparmor` when the kernel enforces AppArmor |
| `vz` | Nothing. It uses `codesign`, which ships with macOS. |

Setup checks the sha256 of every pinned download before it installs it.

## Limits to know before you pick

- **Linux tools.** Every Linux provider also needs `iproute2`, `nftables` and `e2fsprogs`. Setup installs packages with `apt-get`. On a host without it, setup stops and names the tools to install.
- **Firecracker version.** Setup keeps an installed `firecracker` of 1.13.0 or newer, and refuses an older one.
- **Guest kernel.** On Firecracker and `vz`, the daemon downloads a guest kernel the first time it starts.
- **Firecracker disk.** Firecracker needs `/var/lib/shard` on XFS or Btrfs. On another filesystem it needs 20 GiB free for an XFS image, which it mounts over `/var/lib/shard`, so that directory must be empty.
- **Sysbox tenants.** Sysbox CE maps every sandbox to the same host user ID range. Two Sysbox sandboxes are isolated from the host, but not from each other.
- **runc and root.** runc has no user namespace, so root in the sandbox is root on the host.
- **No `--provider`.** A daemon started without it picks `sysbox` or `runc` only when that provider made the sandboxes already under its root.

## Change the provider later

A host runs one provider, and only that provider can read its sandboxes. Setup has no option to change it, and the daemon refuses a different `--provider`. To change it, start the host over:

1. Remove every sandbox. List them with `shard list --all`, and remove each with `shard remove --force <name>`.
2. Run `shard setup` and choose **Uninstall shard**. It removes the daemon and keeps the data in `/var/lib/shard`.
3. Delete that data with the commands the uninstall note prints. This deletes the snapshots, images, secrets and network policies of the host.
4. Run `shard setup` again and pick the new provider.
5. If you installed [`shard serve`](/docs/guides/remote/) by hand, start it again with `systemctl start shard-serve`.

If a step is missing, setup's checks name what is still in the way and change nothing.
